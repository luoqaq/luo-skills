# ui-prototype Skill 设计定稿（2026-09-24）

立项依据与竞品调研见 [research/pc-prototype-skill-landscape.md](../../../research/pc-prototype-skill-landscape.md)。本文档只记录定稿的设计决策和 SKILL.md 骨架，不重复调研内容。

## 定位

名称：`ui-prototype`（端无关架构定稿后改名；曾先后考虑 `desktop-ui-prototype`、`pc-ui-prototype`）。

架构端无关：五阶段流程对 PC 和移动端通用，设计知识按端拆参考文件，由 SKILL.md 按任务条件加载。v1 只写 PC 参考文件，移动端留接口后续补。

通用 skill，不绑定宿主（Kimi Code / Codex 都能跑），不引用宿主专属工具名。截图步骤写成能力要求："使用可用的浏览器或截图工具"。

触发场景：PC 端或移动端的页面原型——工作台、后台页面、dashboard、列表/详情页、分析页、表单页。移动端任务走同一流程，但 v1 移动端参考文件尚未编写，设计判断依赖通用流程，需在简报中声明。
明确不适用：营销落地页、静态艺术图（海报/PNG 画布类）。这些应在描述中引导到其他 skill 或明确拒绝。

## 已拍板的决策

| 决策点 | 结论 |
|---|---|
| 宿主环境 | 通用 skill，两边都能跑 |
| 单次交付范围 | 不限页面数量，但阶段 1 必须先确认页面清单再动手；清单确认后的小修不重复确认 |
| 端范围 | 架构端无关（SKILL.md 通用流程 + 按端加载参考文件）；v1 只写 `pc-design-reference.md`，`mobile-design-reference.md` 留接口后续补 |
| 方向选择 | 用户未给明确视觉方向时，默认产两个轻量视觉方向稿截图供选，选定后补完整简报；已给方向则跳过 |
| 视觉验收 | 硬门槛；宿主无浏览器工具时，交付必须显式声明"未经视觉验收"并给出人工预览方式 |
| 文件结构 | `SKILL.md` + 按端拆分的参考文件；脚本等出现重复机械步骤后再抽 |
| 验证方式 | 调研「如何判断新 Skill 真有改进」一节的 A/B/C 盲测作为 skill 完成后的独立验收任务，不写进 SKILL.md |

## 五阶段流程（SKILL.md 主体）

约束力来自措辞：阶段 1 和 4 用"必须/不得"，阶段 2、3、5 用"默认/应当"。

### 阶段 1：输入契约（硬门槛）

必须确定的信息只有两类——**页面任务**（服务谁、主要动作，一个动词短语）和**交付范围**（页面清单：本次交付哪几个页面、各自的任务）。页面清单确认后不得自动扩充，后续小修不重复确认。

其余信息按优先级获取，不作为提问理由：

- 必须出现的字段、图表、状态清单
- 示例内容（文案、数据量级）：业务逻辑自洽的模拟数据即可，标注为演示数据；不要求接真实业务接口
- 品牌资产（logo、色、字体），没有则记录"无"
- 参考方向与禁用方向
- 目标画布尺寸，未指定则按阶段 4 默认值

已有项目必须先读其设计系统和相邻页面，能提取的信息不从用户那里问。
只有影响范围或核心设计的问题才询问用户，一次最多 2-3 个；不足以构成提问的缺口使用合理默认值，并在设计简报中声明。

### 阶段 2：设计决策（简报先行，无方向时先看图）

分两种路径：

**用户已给明确视觉方向**（参考图、设计系统、具体描述）：沿用，直接产出文字设计简报。

**用户未给方向**：默认先产两个**轻量视觉方向稿**——单屏、真实内容、只表达布局/密度/配色方向，不做完整交互——截图供用户选择。两个方向必须在布局或密度上结构性不同，不能只换配色。用户选定（或要求杂交）后，再基于选定方向补完整简报并继续。

设计简报必须包含：

- 信息层级：第一屏焦点是什么，次要信息如何退后
- 密度档位：紧凑（数据工作台）/ 标准 / 疏朗（表单向导），并说明选择理由
- 布局骨架：导航形式（侧边/顶部）、分区结构
- 视觉方向：配色、字排的具体选择及其与业务语境的关系

禁止使用"高级、科技感、极简、大气"这类形容词作为决策依据——每个选择必须能追到角色、任务或品牌。

### 阶段 3：原型实现

- 独立 HTML/CSS/JS 单文件优先；已有项目则按其技术栈
- 文案和数据必须业务自洽：禁止 lorem ipsum、占位数字、"Test User"；模拟数据要符合业务逻辑且内部一致，并标注为演示数据
- 交互只实现演示主要动作所需的部分，不做全功能
- 图像素材优先级：项目已有真实素材 > 授权素材库 > 占位服务/简单 CSS 图形（需说明其功能）；禁止用图像生成模型产出整页 UI 位图冒充页面

### 阶段 4：视觉验收（硬门槛）

- 默认视口按端取：桌面 1440×900 和 1280×800；移动端视口以对应参考文件为准（v1 未编写时按 390×844）。用户指定画布则覆盖默认值
- 逐项检查：第一屏焦点、密度与留白、字排阶梯、对齐、截断/溢出、颜色一致性、真实状态（空/加载/错误按需）、主要操作可见性
- 至少完成一轮截图审查；发现问题必须修改并重拍；未发现问题则记录检查结果，不为满足流程制造无意义微调
- 修订有界：一轮批量截图、一次批量修复，至多两轮后停止打磨
- 截图不能替代点击验证：主要动作的交互路径需实际操作一遍
- 宿主无浏览器/截图工具时：不得假装验收过，交付中必须显式声明"未经视觉验收"，并给出人工预览方式（启动命令 + 访问地址）

### 阶段 5：交付

交付物清单：

- 源文件路径和预览方式（命令 + 地址）
- 最终桌面截图（两个视口，或验收豁免声明）
- 设计简报（阶段 2 产出）及关键选择说明
- 未验证部分清单
- 明确提示：这是原型，不是生产实现

## 参考文件 pc-design-reference.md 内容提纲

- 信息密度三档位的适用场景与参数（行高、间距、字号、表格密度）
- 表格/筛选/表单/图表的 PC 布局惯例（筛选区位置、操作列、分页、空状态）
- 侧边导航 vs 顶部导航的取舍条件
- 字号字重阶梯与状态色规范（成功/警告/错误/中性的克制用法）
- 反模式清单针对具体问题而非布局类别：无主次之分的等权卡片网格、把需要连续比较的数据拆进多个卡片、无意义渐变与投影、emoji 当图标、无语境插画。每条附豁免条款：用户明确要求时，brief 优先于禁令
- 布局匹配指引：什么任务适合什么布局、为什么（如监控模块适合卡片、连续比较的数据适合表格），防止禁令把所有页面推向单一风格
- 中文界面的字排要点（中西文混排、数字用 tabular-nums）

## 明确不做

- 不内置 HTML 模板或设计系统 starter（会把"熟悉的模板"内置化，违背初衷）
- 不接外部设计服务/API
- 不写评分公式或自动审美打分
- 不做营销落地页（后续可另设模式）
- v1 不编写 `mobile-design-reference.md` 的内容，仅留接口
- 不预先写脚本（出现重复机械步骤后再抽）

## 完成后的验证（独立任务，不属于 skill 本身）

按调研「如何判断新 Skill 真有改进」一节执行：选 2-3 个真实需求（工作台、列表、详情各一），固定模型、画布、内容和素材，盲比 A 原始提示 / B 现有 frontend-skill / C 本 skill。审美结果由人做成对选择；自动检查只负责可运行性、溢出和内容缺失。再单独隔离"有无参考图""有无截图复盘"两个变量。
